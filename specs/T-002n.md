# Spec T-002n: Manager corrects a customer's details (API, audit, customer page)

Ticket: [tickets/T-002n-manager-edits-customer-details.md](../tickets/T-002n-manager-edits-customer-details.md).
Package 4 ([work packages](T-002-work-packages.md)). Amends D4; new decisions D8, D9
(ARCHITECTURE.md section 16). Depends on T-002f, T-002i, T-002j (all built).

## Questions and assumptions

- A1. Editable: `name`, `contact_name`, `email`, `phone`, `billing_address` (`line1`, `line2`,
  `town`, `county`, `postcode`). Not editable: `id`, `customer_type`, `payment_terms_days`,
  `notes` (internal, not in the API), counts, job site addresses (job data), anything on
  jobs/reports/photos/checklists.
- A2. A customer edit does **not** reopen reviewed reports and does **not** change any report's
  `version` (D9). "Reviewed" approves the painter's evidence (notes, checklist, photos), not the
  customer's contact record; reopening up to 12 reports for a phone-number fix would flood the
  review queue. The change is visible in every affected report's History instead.
- A3. One audit event per save, stored once against the customer (`customer_id`); each report's
  history reads it through the report's job (D8). No per-report copies.
- A4. Impact is "jobs, reports (of which reviewed) and issued invoices of this customer", counted
  when read. Invoices have no address snapshot, so issued invoices show the new billing address
  (backlog B12).
- A5. Validation is tolerant (D10 below), applies only to the keys sent, and has a Python and a
  TypeScript twin that share one case table.
- A6. No customers list; the customer page is reached from a report (and from invoice rows is
  out of scope).
- A7. The 409 carries `current` like report PATCH, so T-002o can reuse the conflict view.

## Summary

Customers get a `version`, `last_changed_at/by`; three manager endpoints (read, PATCH, history)
plus a `customer_id` filter on the reports list; `customer.edited` audit events linked to the
customer and shown on the customer page and on every report of that customer; a web customer
page with an edit form, impact notice and the T-002j conflict handling.

## Patterns

None new. Same shape as T-002i: a pure `diff_customer(customer, edits) -> list[FieldChange]`
drives no-op detection, the audit entry and the response. Validators are plain functions
(`backend/app/schemas/customer_write.py`, twin `shared/src/customer/validation.ts`), like the
company-name rule. A Strategy for per-entity history would be a Factory with two products; a
plain `or_` in the query is enough.

### PATCH body `CustomerUpdate` (Pydantic, `extra="forbid"` at every level)

- `version` strict int >= 1, required. At least one editable key, else 422 `loc ["body"]` "Send
  at least one field to change."
- `billing_address` is a partial object (`AddressUpdate`, at least one key); only the parts sent
  change.
- Every other key: 422 `extra_forbidden` naming it (ticket scenario 8).
- All problems reported at once (one `errors` entry each).

### Validation (D10), applied per sent key, in this order (first failure per field wins)

Common text rule (`clean_text` in `backend/app/schemas/text.py`, twin `cleanText` in
`shared/src/customer/validation.ts`). Both twins do exactly this, in this order, the same order
as the company name (T-002c):

1. Trim: strip only U+0020 from both ends.
2. Blank: a required field gives its "Enter ..." message; an optional field becomes null (and
   no further check runs).
3. Length: more code points than the field's maximum (after trimming) gives "Use N characters
   or fewer.".
4. Forbidden characters: the company-name set (U+0000-001F, U+007F-009F, U+200B-200F,
   U+202A-202E, U+2066-2069, U+FEFF, lone surrogates U+D800-DFFF) gives "Remove control
   characters.".
5. Then the field's own format rule from the table (email, phone).

So a 200-character name containing a tab reports the length message, not the control-character
one. Postcode is the exception: it does not use `clean_text`; in UK-only mode blank, over 10
characters and forbidden characters all give the one postcode message (checked in that order,
then the format), and with UK only off every failure gives "Enter a postcode." (T-002p A5).

Phone and postcode rules depend on the T-002p setting `uk_only_contact_details`; the table below
is the UK-only default as amended by T-002p (phone message "Enter a UK phone number such as
07700 900123."; international `+` numbers only when the setting is off). See
[T-002p.md](T-002p.md) for the other mode and for where these two fields are validated.

Reuse `contains_forbidden_character` from `backend/app/schemas/settings.py` (move it to
`backend/app/schemas/text.py` and import it in both; keep the twin `companyName.ts` in sync by
having it import the same set from a new `shared/src/text/forbidden.ts`).

| Field | Required | Max | Rule after `clean_text` | Stored | Message |
|---|---|---|---|---|---|
| name | yes | 120 | non-empty | trimmed | "Enter a name." / "Use 120 characters or fewer." |
| contact_name | no | 120 | blank → null | trimmed | "Use 120 characters or fewer." |
| email | no | 254 | blank → null; `^[^\s@]{1,64}@[^\s@.]+(\.[^\s@.]+)+$` | trimmed, case kept | "Enter an email address such as name@example.co.uk." |
| phone | no | 30 | blank → null; only `0-9`, space, `-`, `(`, `)`, leading `+`; digits-only form (drop space, `-`, `(`, `)`, and a `(0)` right after `+44`) matches `^0\d{9,10}$` or `^\+44\d{9,10}$` (setting off: also `^\+[1-9]\d{7,14}$`) | trimmed, runs of spaces collapsed to one | "Enter a UK phone number such as 07700 900123." (setting off: "..., or an international number starting with +.") |
| line1 | yes | 100 | non-empty | trimmed | "Enter the first line of the address." |
| line2 | no | 100 | blank → null | trimmed | |
| town | yes | 60 | non-empty | trimmed | "Enter a town or city." |
| county | no | 60 | blank → null | trimmed | |
| postcode | yes | 10 after trim (inner spaces count) | remove all spaces, upper case, `^[A-Z]{1,2}[0-9][A-Z0-9]?[0-9][A-Z]{2}$` | `OUTWARD INWARD` (inward = last 3) | "Enter a UK postcode such as BS6 5QA." |

`null` for a required field: "Enter ..." message (not a type error). Non-string: Pydantic type
error. Normalisation is applied before the no-op compare, so `bs14sb` against stored `BS1 4SB` is
a no-op. Only sent keys are validated: an old stored value that fails today's rules never blocks
an unrelated edit.

**One case table:** `shared/src/customer/validationCases.json` (`[{field, input, ok, stored |
message}]`, at least 40 cases including every forbidden range, astral emoji accepted in names,
`+44 (0)117 496 0123`, `GIR 0AA` refused, `ec1a 1bb` accepted). Read by
`backend/tests/test_customer_validation.py` (path from the repo root) and by
`shared/src/customer/validation.test.ts`, so the twins cannot drift.

### Order of checks and outcomes (service `update_customer`)

1. Body validation → 422 (nothing loaded). Since T-002p in two stages: Pydantic for every field
   except phone and postcode, then `validate_contact_fields` with the company setting for those
   two (same 422 shape), both before the customer lookup.
2. `session.get(Customer, id, with_for_update=True)` → 404 "Customer not found."
3. `version` mismatch → 409 `version_conflict`, detail "This customer was changed after you
   loaded it.", extensions `current_version`, `last_changed_at`, `last_changed_by`, `current`
   (stored values of exactly the sent keys; for `billing_address` only the sent parts).
4. Diff against normalised values. Empty → rollback (release lock), 200 current record, same
   version, no event.
5. Apply; `version += 1`; `last_changed_at = now`; `last_changed_by_id = user.id`;
   `record_event(action=customer_edited, customer_id=customer.id, changes)`. No report row is
   touched (no version bump, no reopen).
6. Commit; return `get_customer_record`.

Concurrency: row lock + compare, as in `services/review.py`. Report edits and customer edits lock
different rows, so they never block or conflict with each other.

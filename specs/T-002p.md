# Spec T-002p: "UK only" for customer contact details is an admin setting

Ticket: [tickets/T-002p-uk-only-contact-setting.md](../tickets/T-002p-uk-only-contact-setting.md).
Decision by Paul, 2026-11-08: "UK only should be an admin config setting". Amends D10 (T-002n).
Depends on T-002b/c/e (settings), T-002f (audit), T-002n (customer validation). Backend and
contract first; the frontend follows.

## Summary

A boolean company setting `uk_only_contact_details`, default **true**. Admin changes it through
the existing `PATCH /admin/settings`. Everyone reads it from the public `GET /branding` so client
forms validate the same way the server does. It changes only how phone and postcode are validated
on **new** customer edits; stored data is never revalidated and the seed is unchanged.

## Decisions and assumptions

- A1. Field name `uk_only_contact_details` (snake_case like every other contract field; the
  request said `ukOnlyContactDetails`, which would be the only camelCase name in the API).
- A2. Migration number: the head was `0007`, so this is `0008` and the unbuilt T-002m `job_types`
  migration becomes `0009` (specs updated; the chain stays linear).
- A3. Setting off means "any country", not "no rules": postcode 2-12 characters, phone `+` and
  8-15 digits. Email, names and address lines are unchanged.
- A4. Phone, UK only: national `0` + 9 or 10 digits, or `+44` (optionally followed by `(0)`) + 9
  or 10 digits. `+44 0117 496 0123` (national 0 kept outside brackets) is therefore **rejected**
  when UK only and accepted when off (as a well-formed international number). `0044...` is
  rejected in both modes (unchanged from D10).
- A5. Postcode, off: ASCII letters, digits, spaces and hyphens, 2-12 characters after trimming
  U+0020, starting and ending with a letter or digit. Stored upper case with runs of spaces
  collapsed. A value the UK rules accept still gets the UK form (`bs65qa` -> `BS6 5QA`). Any
  failure, including control or bidi characters, gives "Enter a postcode." (the starting/ending
  rule is a refinement of "any 2-12 characters": it stops `--` and `-12` being stored).
- A6. Messages: UK only keeps the UK-specific ones: postcode "Enter a UK postcode such as BS6
  5QA." and phone **"Enter a UK phone number such as 07700 900123."** (the old text offered
  international numbers, which UK-only refuses). Off: phone keeps the D10 message ("...or an
  international number starting with +."), postcode "Enter a postcode.". Length and control
  character messages are the same in both modes.
- A7. Turning the setting on or off never touches stored customers. Because only sent keys are
  validated, a stored `+1 202 ...` phone does not block an unrelated edit after the setting goes
  back to on.

## Patterns

None new. The mode-independent fields stay Pydantic field validators. Phone and postcode move out
of the request model because a field validator cannot see a database setting; the service
(`services/customers.validate_contact_fields`) validates them with the pure functions
`validate_phone(raw, uk_only=...)` and `validate_postcode(raw, uk_only=...)` and writes the
normalised values back onto the update. A validation-context or dependency design was rejected:
FastAPI does not pass context to body models, and a dependency would depend on resolution order.

Consequence: a body with an error in a mode-independent field reports only that (and the other
Pydantic errors); phone and postcode problems appear on the next attempt, after those are fixed.
The 422 shape is identical (`errors[].loc` `["body","phone"]` / `["body","billing_address",
"postcode"]`, `message`). The mode check runs before the customer lookup, so 422 still precedes
404 and 409.

## Data

Migration `0008_uk_only_contact_details` (down_revision `0007`): `company_settings.
uk_only_contact_details boolean not null default true`. Existing row becomes true. Downgrade
drops the column. Seed untouched (`company_settings` is preserved across reseeds).

## API (contract `api/openapi.yaml` v0.4.0, `x-ticket: T-002p`)

- `Branding` and `AdminSettings` gain required `uk_only_contact_details: boolean`.
- `AdminSettingsUpdate` gains optional `uk_only_contact_details: boolean`. Only a real boolean
  (null, strings, 0/1 give 422 "Send true or false."). Admin only (manager and painter 403, as
  the whole endpoint). Same no-op rule (unchanged value: 200, no event), same atomic save.
- `AuditField` gains `uk_only_contact_details`; change records hold booleans (`old_value`,
  `new_value` already allow boolean). One event can carry it next to `company_name` or theme
  changes.
- `updateManagerCustomer` description updated for both modes.

## Frontend work (for the frontend engineer)

1. Admin Settings page: a labelled switch/checkbox "UK customers only" with help text ("Customer
   postcodes and phone numbers must be UK ones. Turn off to allow other countries."), saved with
   the same pattern as the other settings (own Save, 200 confirmation, 422/403/500 states).
2. Customer edit form: `validateCustomerForm`, `normalisedValue` and `VALIDATORS[f](raw, ukOnly)`
   take `ukOnly` from branding (`useBranding().uk_only_contact_details`; treat a missing value as
   true). The twin `shared/src/customer/validation.ts` already accepts it (default true).
3. Field hints and placeholders follow the mode (postcode "BS6 5QA" vs a neutral one; phone
   hint). The server message is shown unchanged for 422.
4. History panel: new field label "UK-only contact details" with On/Off (done in
   `shared/src/history.ts`).

## Test notes

Backend: `test_uk_only_setting_api.py` (default, admin toggle, audit event with booleans,
no-op, combined change, strict boolean, manager/painter/anonymous refused, phone and postcode in
both modes, stored values untouched, email unchanged), `test_customer_validation.py` and
`test_customer_edit_api.py` (case table through the pure validators in the right modes and through
the API with the setting set per case), `test_branding_api.py`, `test_migrations.py` (0008 up and
down, head). Shared: `validation.test.ts` over the same table.

Case table: `validationCases.json`. Phone and postcode cases carry `ukOnly` (true or false), the
mode the case is evaluated under, and appear once per mode. Cases for other fields have no
`ukOnly` and are run in both modes by both test suites.

## Out of scope

Per-field toggles, other countries' postcode formats, phone formatting for display, revalidating
existing customers, mobile.

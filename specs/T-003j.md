# Spec T-003j: Interrupted submissions and duplicates (idempotency)

Ticket: [tickets/T-003j-interrupted-submissions-and-duplicates.md](../tickets/T-003j-interrupted-submissions-and-duplicates.md).
Package E. Design sections 3.4, 6. Kind: backend tests (no new endpoint) + mobile. T3-5.

## Questions and assumptions

- A1. Two devices with different drafts: first submit wins (T3-5); the loser's extra photos stay
  on that phone as "Not sent: report already submitted"; the office is not told.
- A2. Manager edits before an offline submit arrives cannot happen to a draft (managers cannot
  see drafts); scenario 7 therefore means "the report was already submitted (and maybe
  reviewed/edited) when this device's submit arrives" → `already_submitted`, manager state
  untouched.

## Summary

Prove "repeating is always safe" end to end: the server mechanisms exist from T-003f/g/h
(job-keyed report, client photo ids, `submission_id`); this ticket adds the idempotency test
matrix, the app's truthful recovery after a kill or lost reply, and duplicate gallery detection.

## Backend

`tests/test_idempotency_matrix.py`: every operative write repeated (sequentially and with two
threads through a `Barrier`) yields one effect: draft PATCH, photo register, content upload,
delete, submit (same id), submit (different ids). Audit: one `report.submitted` per report.
Manager list: one report per job. Fix any defect found (expected: none).

## Mobile

- `submission_id` created once at confirm and reused for every retry (stored before the first
  send); a second confirm tap while `submit_queued` is ignored (button disabled, and the store
  refuses a second id).
- Recovery on start: for each `submit_queued` job, `getOperativeJob` first: `submitted` with my
  `submission_id` → mark submitted; with another id → "This report was already submitted from
  another device", photos kept, unsent ones "Not sent: report already submitted"; still draft →
  send the queued submit.
- Lost reply on a photo: re-sending register/content gets 200 and the photo becomes Sent.
- Duplicate gallery pick: compare `original_sha256` (computed at import for gallery photos only,
  off the UI thread) with the job's photos → "This photo is already on this job." and not added;
  the same photo on another job is allowed. Server 409 `duplicate_photo` is the backstop.
- Reinstall: a new DB; the job list and `getOperativeJob` show "Submitted" and server photos as
  "Sent" with server thumbnails; Submit is not offered for a submitted report.

Integration suite cases below use the fault proxy mode "drop the response after the server

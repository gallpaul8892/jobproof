# Spec T-002e: Admin chooses the colour scheme (WCAG AA enforced)

Ticket: [tickets/T-002e-admin-chooses-colour-scheme.md](../tickets/T-002e-admin-chooses-colour-scheme.md).
Package 1, last ticket ([work packages](T-002-work-packages.md)). Decision D6. Depends on T-002c, T-002d.

## Questions and assumptions

- A1. Low contrast is **rejected**, never warned (default; D6). "Reset to default" is always
  reachable on the Settings page, which itself always renders legibly (it is themed by the same
  rule, so a stored theme can never be unreadable).
- A2. Contrast is compared **unrounded** against 4.5; the reported ratio is rounded to 2 decimals
  half-up, except a failing ratio is never reported as 4.50 (shown 4.49).
- A2a. (Review round 1, architect decision.) Primary and accent text also sit on the surface colour
  `#F4F7F2` (demo role labels, links in hovered rows, the selected preset card), so each must reach
  4.5:1 against **both** white and the surface colour. The ratio measured and reported is the
  lower of the two. This supersedes the ticket's boundary table, which measured white only:
  `#767676` is 4.54 on white but 4.20 on the surface, so it is now **rejected**; `#727272`
  (4.81 / 4.45) is rejected; `#717171` (4.88 / 4.52) is the lowest grey accepted. `#777777` 4.14,
  `#4CAF50` 2.57 and `#FFD400` 1.32 are the reported (surface) ratios; on white alone they are
  4.48, 2.78 and 1.43. The default theme and the four presets pass on both (lowest: Navy accent
  7.97, Burgundy accent 8.16).
- A2b. Company-name trimming and validation are identical on server and web: only the ordinary
  space U+0020 is trimmed; after that the name is rejected if it contains U+0000-001F,
  U+007F-009F, U+200B-200F, U+202A-202E, U+2066-2069 or U+FEFF. The `create-admin` full name uses
  the same rule.
- A3. Only primary and accent are editable; background, surface and text stay at defaults.

## Summary

Extend `PATCH /admin/settings` with `theme {primary, accent}`, validated for format then
contrast on the server; Settings page gets presets, two colour inputs with live ratio, a preview
panel and Reset to default.

## Patterns

None. The contrast rule is a pure function implemented twice (Python, TS) and tested against
one shared table of cases.

## Data

No schema change (columns exist from T-002a; DB check enforces upper-case `#RRGGBB`).

## API

`PATCH /api/v1/admin/settings` body gains `theme: {primary, accent}` (both required when
`theme` is present; `extra="forbid"` inside). Order of checks:
1. Format (`^#[0-9A-Fa-f]{6}$`, both present): 422 `validation_error`, `loc` `["body","theme",
   "primary"]` etc. `green`, `#12345`, `#GGGGGG`, `1F5130`, missing accent all land here.
2. Normalise to upper case.
3. Contrast of each colour vs `#FFFFFF` and vs the surface colour (`#F4F7F2`); the lower ratio
   counts. If any fails, 422 `contrast_too_low`, `detail: "Colours must have at least 4.5:1
   contrast against both white and the surface colour."`, `errors` one entry per failing
   colour: `{loc: ["body","theme","primary"], message: "Contrast 2.57:1 against the surface
   colour is below the required 4.5:1.", measured_ratio: 2.57, required_ratio: 4.5}` (the message
   says "white" instead when white is the lower).
Name and theme validate independently but the request is atomic: any error, nothing saved.
Unchanged fields are not touched (scenario 9).

## Backend

- `backend/app/branding/contrast.py`: `relative_luminance`, `contrast_ratio`, `meets_aa`,
  `report_ratio`, `weakest_contrast` (lower of white and surface, with which one; same formulas as `shared/src/branding/contrast.ts`, T-002d).
- `schemas/settings.py`: `ThemeUpdate` with pattern-validated fields and an upper-case
  normaliser.
- `errors.py`: `ProblemError` gains optional `errors: list[dict]` and `extensions: dict[str,
  Any]` (merged into the body after the standard members; extension keys may not override
  standard ones). Package 2 uses `extensions` for 409s; nobody else edits `errors.py`.
- `services/settings.py`: contrast check after Pydantic, raising
  `ProblemError(422, "contrast_too_low", ..., errors=[...])`; then the T-002c update path, now
  including `theme_primary`/`theme_accent` in the changed-field list.

## Shared

- `shared/src/branding/presets.ts`: `PRESETS = [{id: "forest", name: "Forest", ...DEFAULT
  primary/accent imported from defaults.ts}, {navy "#1F3A5F" "#2B4C7E"}, {charcoal "#2B2B2B"
  "#444444"}, {burgundy "#7A1F2B" "#8A2433"}]` (Forest's codes are imported, not repeated).
- `shared/src/branding/branding.test.ts`: every preset colour >= 4.5:1 (Navy accent 8.61,
  Charcoal 14.16/9.74, Burgundy 10.20/8.82); the ticket's boundary table.
- `normaliseHex(input) -> string | null` (accepts `#rrggbb` any case, returns upper case).
- `shared/src/api/errors.ts`: `FieldError` gains optional `measured_ratio`/`required_ratio`,
  and `ApiError` gains `readonly problem: Record<string, unknown> | undefined` (the parsed
  problem body, so callers can read extension members). Package 2 relies on `problem` for
  409 bodies; nobody else edits this file.

## Web

`pages/settings/ColourSchemeForm.tsx` and `ThemePreview.tsx` on the Settings page, below the
company name form (separate Save button, separate request: scenario 9).

- Presets: a radio group of four cards (name and two swatches). Picking one fills both inputs.
- Custom: two text inputs "Primary colour (header and buttons)" and "Accent colour (links and
  focus)", each with a native `<input type="color">` beside it bound to the same value (the
  colour input always yields lower-case `#rrggbb`; normalise). Under each: "8.53:1 against
  the surface colour, passes" or, as an error, "1.32:1 against the surface colour, needs 4.5:1"
  (the lower of the white and surface ratios, naming which background it is) (`aria-describedby`, `aria-invalid`).
- Save disabled while unchanged, malformed or failing contrast. Server 422 messages are shown
  beside the field as well (the server is authoritative).
- Preview panel: sample header bar with the company name, a primary button, a link and a
  focused input, rendered inside a `<div>` whose `--jp-primary`/`--jp-accent` are set with the
  React `style` prop (CSSOM: CSP-safe). It shows the **last valid** pair while an input is
  invalid (scenario 4). It never changes the real app theme before saving.
- Reset to default: a secondary button, always enabled, opens a confirm dialog ("Reset colours
  to the default green?"), then fills Forest; the admin presses Save to persist (same flow as any
  change, so it is audited).
- On save success: the mutation updates the `branding` query, the provider calls `applyTheme`,
  so the whole app (including the admin's header) switches at once; other users get it on next
  load or focus (T-002c caching policy).

## Summary

Job types stop being a painting-only Postgres enum and become data (a `job_types` table with
labels, returned by the API), and the seed gains `SEED_PROFILE` (`painting` default,
`tree_surgery`) producing the same shape of dataset with different content.

## Patterns

- **Strategy-like data record** for seed profiles: `SeedProfile` (frozen dataclass: job types with
  labels, counts, price ranges, titles, checklists, captions, customers and addresses, done-notes)
  and a registry `PROFILES = {"painting": PAINTING, "tree_surgery": TREE_SURGERY}`. The dataset
  builder takes a profile instead of reading module constants. A data record, not a class
  hierarchy: profiles differ only in content, never in behaviour.

## Data

Migration `0007_job_types` (down_revision `0006`):
1. Create `job_types (code text pk CHECK (code ~ '^[a-z][a-z0-9_]{1,39}$'), label text not null
   CHECK (char_length(label) BETWEEN 1 AND 60), position smallint not null, unique (position))`.
2. Insert the six painting types with today's labels (Interior repaint, Exterior repaint,
   Wallpapering, Kitchen cabinet spray, Staircase woodwork, Commercial unit), positions 1 to 6.
3. `ALTER TABLE jobs ALTER COLUMN job_type TYPE text USING job_type::text`, add FK
   `fk_jobs_job_type_job_types` (`ON DELETE RESTRICT`), index on `jobs.job_type`.
4. `DROP TYPE job_type`.
Downgrade: refuse if any job uses a code outside the six; recreate the enum, convert the column
back, drop the FK and table.

Seed: `job_types` is truncated and loaded from the profile like any other table (the painting
profile loads the same six rows). The FK means jobs can only use loaded codes.

Tree-surgery job types (code, label, count; counts sum to 60): `crown_reduction` Crown reduction
14, `felling` Felling 10, `stump_grinding` Stump grinding 9, `hedge_trimming` Hedge trimming 10,
`tpo_check` TPO/conservation area check 5, `storm_clearance` Emergency storm clearance 6,
`grounds_clearance` Commercial grounds clearance 6. Content from the ticket (checklists,
captions), Glasgow and Central Belt addresses (G, PA, ML, FK postcodes), `07700 900xxx` phones,
`example.co.uk` emails, GBP prices per type.

**Shape rule:** both profiles produce 60 jobs, 60 reports, 9 awaiting review (same submitted
offsets), 52 invoices with the identical status distribution, the same edge cases (no-photo
report, long notes, multi-job landlord). Achieve this by keeping every structural random draw in
the same order and only swapping content lookups, so the painting profile output is
byte-identical to today's (scenario 2).

## API (contract delta, apply with this ticket)

- `JobType`: from an enum to `{type: string, pattern: "^[a-z][a-z0-9_]{1,39}$"}`.
- `ReportSummary` and `JobDetail`: add required `job_type_label: string`.
- Bump `info.version` to 0.3.0; regenerate the client. Non-breaking for responses (codes keep
  their values); the TS type widens from a union to `string`.

## Backend

- `models/work.py`: `Job.job_type: Mapped[str]` with FK; new `models/catalogue.py` `JobTypeRow`.
  Remove `JobType` from `models/enums.py`.
- `services/reports.py`: join `job_types` for `job_type_label` (in the existing summary and detail
  queries; no extra statement).
- `seed/profiles/__init__.py` (`SeedProfile`, `PROFILES`, `get_profile(name)`),
  `seed/profiles/painting.py` (today's catalogue content moved, unchanged),
  `seed/profiles/tree_surgery.py`; `seed/dataset.py` takes a profile; `seed/__main__.py` reads
  `SEED_PROFILE` (unset = `painting`; unknown: exit 1 with "Unknown SEED_PROFILE 'x'; choose
  painting or tree_surgery"); the local/test guard is unchanged and checked first.
- `config.py`: no change. `SEED_PROFILE` is read by `seed/__main__.py` from `os.environ`, not
  added to `Settings`, so a typo can only break seeding, never backend startup.

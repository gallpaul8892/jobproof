# Spec T-002k: Dashboard review queue (next 5 to review, oldest first)

Ticket: [tickets/T-002k-dashboard-review-queue.md](../tickets/T-002k-dashboard-review-queue.md).
Package 2, first ticket ([work packages](T-002-work-packages.md)). Depends on T-001d only.

## Questions and assumptions

- A1. The queue sits **above** "Recent reports", directly under the stat cards (default: keep both).
- A2. No colour threshold on "waiting".
- A3. "Waiting N days" counts whole Europe/London calendar days between the submitted date and
  the dashboard's `as_of` date: 0 "Waiting since today", 1 "Waiting 1 day", n "Waiting n days".
  Computed from `as_of` (not the browser clock) so FIXED_NOW tests are deterministic.

## Summary

`review_queue` on the dashboard response and a `sort=submitted_asc` option on the reports list,
plus a "Review queue" panel on the dashboard.

## Patterns

None.

## Data

No migration. Existing indexes: `ix_job_reports_review_status`, `ix_job_reports_submitted_at`
(desc; Postgres scans it backwards for ascending order). Volumes are tiny; no new index.

## API

- `GET /api/v1/manager/dashboard`: new required `review_queue: ReportSummary[]` (max 5):
  awaiting review, `submitted_at` asc, then `job_reference` asc. Existing fields unchanged.
- `GET /api/v1/manager/reports`: new `sort` query param, `ReportSort` = `default |
  submitted_asc`. Missing or `default`: today's order. `submitted_asc`: `submitted_at` asc, then
  `jobs.reference` asc. Anything else: 422 `validation_error` (`loc` `["query","sort"]`).
- Manager only, as before.

## Backend

- `services/reports.py`: `ReportFilters` gains `sort: ReportSort = "default"`; `list_reports`
  picks one of two `order_by` tuples. New `review_queue(session, today, limit=5)` reusing
  `_summary_from`/`_summary_columns`, `where review_status = awaiting_review`, the
  `submitted_asc` order.
- `services/dashboard.py`: add `review_queue=...` (one extra SQL statement; the dashboard goes
  from 3 to 4 statements, under the bound of 6 in `test_performance_logging.py`).
- `routers/manager.py`: `sort: ReportSort = "default"` in `report_filters` (a `StrEnum` in
  `models/enums.py` or a `Literal`; either generates the 422).
- `schemas/manager.py`: `Dashboard.review_queue: list[ReportSummary] = Field(max_length=5)`.

## Shared

- `filters.ts`: `ReportFilters.sort?: "submitted_asc"` parsed from the URL (`sort=submitted_asc`
  only; anything else dropped); serialised back to the URL; passed through in `useReports`.
  `default` is never written to the URL.
- `format/dates.ts`: `waitingLabel(submittedAt: string, asOf: string): string` (A3), using the
  existing London date helper.

## Web

- `pages/dashboard/ReviewQueue.tsx`, rendered by `Dashboard.tsx` between the stat cards and
  "Recent reports", inside the same query (same loading skeleton and error-with-retry as the
  page: scenario 9).
- Panel heading "Review queue". Rows (a table on wide screens, stacked cards below 640px, same
  approach as Recent reports): job reference (link), customer, site address (one line), painter
  name (column header text becomes "Operative" in T-002l), submitted date and time, waiting label,
  and a "Review" link (`aria-label="Review JP-1042"`). Both links go to `/reports/<id>`.
- Footer link "View all {n} awaiting review" where `n = reports_awaiting_review`, to
  `/reports?review_status=awaiting_review&sort=submitted_asc`. Shown only when `n > 0`.
- Empty: "Nothing is waiting for review." and no table or link.
- `Reports.tsx`: honours `sort` from the URL; the page heading text does not change; the result
  count text stays "Showing 1-9 of 9 reports". Changing any filter keeps `sort`.
- Cache: after a review (T-002h) the dashboard query is invalidated, so returning to the
  dashboard shows the new queue (scenario 6).

# Spec T-002o: "Apply my changes on top" after an edit conflict

Ticket: [tickets/T-002o-apply-my-changes-on-top.md](../tickets/T-002o-apply-my-changes-on-top.md).
Package 4, after T-002n ([work packages](T-002-work-packages.md)). Decision D11 (ARCHITECTURE.md
section 16). Depends on T-002j (built) and T-002n.

## Questions and assumptions

- A1. Client-only. No endpoint, schema or migration change: the merge needs the version the
  manager loaded (the base, already held by the form), the manager's form, and the latest
  version (one GET). `T-002o` sits in `PENDING_TICKETS` only for uniform bookkeeping (it has no
  `x-ticket` items); remove it at the end.
- A2. Never saves automatically (ticket open question 1). The merged form is shown with a notice
  and the manager clicks "Save changes"; the save is an ordinary PATCH with the latest
  `version`, so the server still guarantees nothing is overwritten unseen.
- A3. Granularity is the field the API edits: `painter_notes`, `manager_notes`, each checklist
  item's `done` and `note`; for customers each of name, contact name, email, phone and the five
  address parts. No merging inside a text value.
- A4. Values are compared after the server's normalisation (blank = null for notes and nullable
  customer fields; postcode and phone normalisers from T-002n), so "  " vs null or "bs1 4sb" vs
  "BS1 4SB" never counts as a clash.
- A5. "Apply my changes on top" is the primary button, "Reload latest" secondary.

## Summary

A pure three-way merge in `shared/` (base = version loaded, mine = form, theirs = latest), used
by the report edit form (T-002j) and the customer edit form (T-002n): fields only the manager
changed are re-applied, fields only the other manager changed take the latest value, fields both
changed to different values become per-field "Keep mine / Keep theirs" choices.

## Patterns

None from GoF. One generic pure function over flat field maps plus two small adapters
(report, customer) that flatten form values to keys and back. A Strategy per entity would be two
classes with one method each; adapters as plain objects `{flatten, unflatten, normalise}` are
enough.

## Data / API / Backend

None. (The 409 `current` values are not needed for the merge; the GET gives the full latest
record and its version.)

## Shared

`shared/src/merge.ts`:

```ts
type Flat = Record<string, string | boolean>;           // form values, keyed
interface MergeAdapter<F> { flatten(form: F): Flat; unflatten(flat: Flat, like: F): F;
  normalise(key: string, v: string | boolean): string | boolean | null; label(key: string): string }
interface Clash { key: string; label: string; mine: string | boolean; theirs: string | boolean }
interface MergeResult<F> { form: F; reapplied: string[]; clashes: Clash[] }
function mergeOnTop<F>(a: MergeAdapter<F>, base: F, mine: F, theirs: F): MergeResult<F>
function resolve<F>(a: MergeAdapter<F>, r: MergeResult<F>, choices: Record<string, "mine"|"theirs">): F
```

Rule per key `k` (with `n = normalise`):
1. `n(mine) == n(base)` (manager did not change it): take `theirs`.
2. else `n(theirs) == n(base)` (only the manager changed it): take `mine`, add to `reapplied`.
3. else `n(theirs) == n(mine)` (both made the same change): take `theirs` (not a clash; it will
   not be sent because it equals the latest).
4. else: clash `{mine, theirs}`; `form[k]` holds `theirs` until resolved.
Keys present in `theirs` but not `base` (not possible today: checklist items cannot be added) take
`theirs`. Order of `clashes` follows the form's display order.

Adapters:
- `shared/src/reportEdit.ts` `reportMergeAdapter`: keys `painter_notes`, `manager_notes`,
  `checklist:<id>:done`, `checklist:<id>:note`; normalise text with the existing `blankToNull`;
  labels from `labels.ts` ("Operative notes", "Manager notes", "Checklist: <label> (done)" /
  "(note)").
- `shared/src/customer/customerEdit.ts` `customerMergeAdapter`: keys `name`, `contact_name`,
  `email`, `phone`, `billing_address.line1` ... `postcode`; normalise with the T-002n validators'
  normalisers (invalid input is compared trimmed as typed, so it is re-applied and then shown
  with its validation message).

Unit tests (`merge.test.ts`): each of the four rules; normalised equality (A4); clash list order;
`resolve` with all-mine, all-theirs (result equals `theirs`, so `buildReportUpdate(latest, form)`
returns null), mixed; idempotence (merge twice with the same latest gives the same form).

## Web

Both `EditReportForm.tsx` and `EditCustomerForm.tsx` (T-002n). Put the shared UI in
`web/src/components/ConflictMerge.tsx` (`ClashChoice` radio group and the merge notice).

- `original` (the base) must become replaceable: today `const [original] = useState(report)`;
  change to `const [original, setOriginal] = useState(report)`. The base stays a snapshot (never
  follows background refetches), which is what makes the three-way merge correct.
- Conflict alert (stale 409): buttons "Apply my changes on top" (primary) and "Reload latest"
  (secondary, unchanged with its confirmation). The `already_reviewed` 409 path (T-002h, review
  button) is unchanged and does not offer this.
- On "Apply my changes on top": button shows "Loading latest..." disabled; `queryClient.fetchQuery`
  of `report(id)` / `customer(id)` with `staleTime: 0`.
  - Failure: alert "Could not load the latest version." with "Try again"; form, conflict view and
    base unchanged (ticket scenario 9).
  - Success: `result = mergeOnTop(adapter, original, form, latest)`; `setOriginal(latest)`;
    `setForm(result.form)`; clear the conflict; keep `lastBody` cleared.
  - Notice (`role="status"`): "Your changes were re-applied to the latest version (changed by
    {last_changed_by.name} at {HH:mm London}). Check them and save." Re-applied fields get a
    subtle "Re-applied" marker (text, not colour only).
  - Each clash: inside the field's area a `<fieldset>` with legend "{label}: changed by you and by
    {name}" and two radios "Keep mine" / "Keep theirs", each followed by the value as plain text
    (`pre-wrap`, scroll box max-height 12rem, `overflow-wrap: anywhere`; boolean values render
    "Done"/"Not done"; null "(empty)"). No radio is preselected. The field's own input stays
    read-only until a choice is made; choosing sets the input to that value, after which it is
    editable again.
  - "Save changes" is disabled while any clash is unchosen, with the hint "Choose a version for
    each field marked as changed by both of you." After all choices, if `buildReportUpdate` /
    `buildCustomerUpdate` against the new base returns null: Save disabled and notice "Nothing
    left to save: the latest version already has the values you kept."
  - Report only: if `latest.review_status === "reviewed"` show the T-002j reopen notice (it reads
    from `original`, so it updates automatically once `original` is the latest).
- Saving uses the new base's `version`. A second 409 shows the conflict alert again; applying on
  top again merges with `base = original` (the version loaded at the previous apply) and `mine =
  form` (choices already made are the manager's values) (scenario 8).
- The "retry after lost success" rule of T-002j still applies to the save after a merge.
- The unsaved-changes guard stays active throughout (the form is dirty against the new base
  whenever anything is re-applied).
- Focus: after a successful apply, move focus to the notice; with clashes, to the first clash
  fieldset.

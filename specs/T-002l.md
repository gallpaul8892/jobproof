# Spec T-002l: Industry-neutral wording

Ticket: [tickets/T-002l-industry-neutral-wording.md](../tickets/T-002l-industry-neutral-wording.md).
Package 3 ([work packages](T-002-work-packages.md)). Decision D7. Depends on T-001d (and, in
practice, packages 1 and 2, whose new screens it also covers).

## Questions and assumptions

- A1. The field worker is "Operative" / "Operatives" (default; one edit to change).
- A2. Data stays as it is: job types, titles, notes, captions and customer names may say
  "painting" (mock data); only chrome changes.
- A3. API names (`painter_id`, `painter`, role `painter`, `/manager/painters`) stay. Recorded as
  naming debt in ARCHITECTURE.md §16 (rename when the painter app is specified, with a
  contract version bump).

## Summary

All interface text that names the trade moves to the label module and becomes neutral.

## Patterns

None.

## Data / API / Backend

None. No contract, generated client or backend change (scenario 4). The demo account labels are
produced by the web from `role` (`roleLabel`), so no backend change is needed.

## Shared

`shared/src/format/labels.ts` gains one wording block, the only place these words live:
```
WORDING = { fieldWorker: "Operative", fieldWorkers: "Operatives",
            fieldWorkerNotes: "Operative notes", allFieldWorkers: "All operatives" }
```
`roleLabel("painter")` returns `WORDING.fieldWorker`. `history.ts` field label for
`painter_notes` uses `WORDING.fieldWorkerNotes`.
